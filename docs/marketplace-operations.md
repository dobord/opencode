# Marketplace: неблокирующие фоновые операции

Статус: реализовано под флагом `marketplace_operations`. Исправления встроенного каталога, демонстрационных пакетов и отображения источников сохранены отдельным коммитом.

## Состояние реализации

Серверная очередь, транспорт и клиенты используют общий механизм:

- `packages/schema/src/marketplace-operation.ts`: идентификаторы, приватные команды и публичные снимки состояний;
- `packages/core/src/marketplace/operation-machine.ts`: переходы жизненного цикла, граница отмены и защита конечного результата от поздних событий;
- `packages/core/src/marketplace/operation-store.ts`: SQLite-очередь, идемпотентный приём, FIFO, один активный исполнитель, проверка версии снимка и явное восстановление прерванных работ;
- новая аддитивная миграция и тесты состояния, хранения, повторных/конкурентных запросов и отделения приватных headers от публичного снимка.
- `operation-runner.ts` получает Location-сервисы на время исполнения, `operations.ts` владеет единственным process-global worker; закрытие запроса не останавливает работу;
- при применении изменение реестра и итог операции записываются одной транзакцией; ошибка последующего обновления конфигурации записывается предупреждением, а не ложным провалом установки;
- отмена прерывает HTTP-тело и Git-процесс, ждёт очистки staging и только затем освобождает очередь; граница применения не прерывается;
- доступны создание (`202`), список, чтение и отмена операций, а также глобальный SSE-снимок `marketplace.operation.updated`; клиент перегенерирован;
- подготовка плана возвращает fingerprint разрешённого плана/commit, доверия и конфликтов; установка проверяет его до материализации;
- Git передаёт реальные счётчики объектов из stderr с обработкой `\r`, материализация — счётчики файлов. Снимки счётчиков объединяются до четырёх раз в секунду, конечный счётчик публикуется немедленно;
- новый `update-all` сохраняет независимый результат каждого пакета в `outcomes`, причём успешный результат записывается в транзакции замены пакета. Ошибка другого пакета и рестарт не отменяют уже сохранённые обновления.

Новый API ограждён opt-in-only флагом `marketplace_operations`: `OPENCODE_FLAGS=marketplace_operations` либо `experimental.marketplace_operations: true`. По умолчанию он выключен даже в dev. Восстановление один раз выполняет process-global worker при старте, не экземпляр хранилища и не HTTP-handler. Это не распределённый планировщик.

- `GET /api/experimental/marketplace/snapshot` читает только кэш, без загрузки отсутствующих каталогов. Отдельная таблица хранит `checking | ready | failed | disabled` для источников; адрес с ошибкой остаётся сохранённым.
- Web/Desktop держат версионированные снимки в controller уровня сервера, а не панели. SSE, повторное открытие и восстановление связи согласуются по версии; редкий резервный запрос используется при разрыве подписки. Поиск, вкладки и независимые ресурсы не блокируются.
- В оболочке доступен центр операций с отменой, историей, предупреждениями, подготовленными планами и независимыми результатами пакетов. Toast обновляет один снимок; закрытие toast не отменяет задачу. Подтверждение плана всегда явное, даже если подготовка завершилась после закрытия панели.
- CLI ждёт ту же операцию, пишет прогресс в stderr и итоговый JSON в stdout. `--detach` возвращает ID; действия `operations`, `observe <id>` и `cancel <id>` позволяют восстановить наблюдение. Для установки с ранее подтверждённым планом поддерживается `--fingerprint`.
- TUI отправляет короткий запрос и сразу возвращает управление. Через «Operations and prepared plans» доступны этапы, результаты, подготовленные планы и отмена; завершение также приходит вне диалога через серверные события.
- При включённом флаге старые синхронные изменяющие endpoints явно отклоняются и направляют вызывающего в operations API: скрытого параллельного пути записи нет. При выключенном флаге сохранён прежний интерфейс и поведение.

Развёртывание локальной сборки ограничено Marketplace-сервером `4410`, с прежним каналом и явным путём к существующей базе. Основной сервер `49374` не обновляется.

## Рекомендация: серверная очередь + центр операций + локальные статусы

Основной вариант — операция принадлежит серверу, а не открытой вкладке. Короткий запрос принимает действие и возвращает `operationID`. Интерфейс продолжает работать, подписывается на изменения и может в любой момент восстановить состояние из серверного снимка.

Три поверхности отображения:

1. **В строке источника или карточке пакета**: текущий этап, реальные счётчики, ошибка или результат. Отключаются только противоречащие действия над этим ресурсом.
2. **Компактный центр операций на уровне оболочки приложения**: количество активных работ, выполняющиеся/ожидающие действия и недавние результаты. Доступен вне настроек Marketplace и после закрытия диалога.
3. **Одно уведомление на операцию**: принятие действия, затем итог с кнопкой «Подробнее». Не создавать новый toast на каждый файл или процент. Закрыть уведомление — не отменить работу.

Пользователь может читать каталог, искать, менять вкладки, работать с чатами и добавлять другие действия в очередь. «Не блокировать интерфейс» не означает одновременно выполнять несовместимые записи в реестр.

Пример строки:

```text
Cloudflare
Установка · Сохранение файлов · 143 из 359
[Подробнее] [Отменить]
```

Для источника:

```text
openai/plugins
https://github.com/openai/plugins
Подключение · Чтение каталога
```

Заголовок по умолчанию — `owner/repository`, ниже — исходный адрес пользователя. Внутренний raw URL можно показывать в технических подробностях, но не вместо адреса источника. Пользовательское имя сохраняется.

| Подключение источника | Очередь → проверка адреса → обнаружение каталога → загрузка → проверка формата → готово/ошибка                                                    | Загруженные байты, если известен размер; количество найденных записей. | Удаление              | Очередь → отключение вклада пакета → фиксация → обновление конфигурации → готово                                                                  | Короткие именованные этапы. Если операция быстрая, не мигать прогрессом искусственно. Общий кэш остаётся до отдельной очистки.                                     |
| Обновление пакета     | Проверка версии → подготовка новой версии → загрузка и материализация → атомарная замена → применение конфигурации                                | Старая версия остаётся активной до фиксации новой. Ошибка подготовки не должна отключать рабочую установку.                                                        |
| Обновить всё          | Родительская операция + результаты каждого пакета                                                                                                 | `Подготовлено 3 из 8`, этап текущего пакета, итоговые ошибки и предупреждения. Семантику фиксации партии нужно выбрать явно, см. ниже.                             |

Пока размер неизвестен — `Loader` и название этапа, без процентов и придуманного ETA. AI-спиннер здесь не подходит. Если Git сообщает 100% объектов, это ещё не 100% установки: материализация и запись конфигурации впереди.

Для Git следует использовать поддерживаемый поток дочернего процесса (`AppProcess.runStream()` либо отдельные stdout/stderr у spawner), принудительно включить `--progress` и стабильный язык служебного вывода. Обрабатывать также обновления через `\r`. Публикацию частых счётчиков объединять, например до 4 раз в секунду; смену этапа и конечный результат доставлять сразу. Сырые stderr и детали ошибки доступны в раскрываемых подробностях, без секретов.

## Серверная модель

Отдельный process-global `MarketplaceOperations` рядом с `MarketplaceRegistry`, а не расширение Session Jobs. Глобальная область нужна потому, что реестр общий: два окна с разными Location всё равно меняют одну ревизию. Исходная Location сохраняется как контекст проверки конфигурации, а не как отдельный независимый реестр.

Worker должен получать Location-сервисы на время выполнения через существующее управление Location и удерживать их жизненный цикл до завершения. Нельзя просто сохранить замыкание из HTTP-handler и запустить его в фоне: оно может сохранить request-scoped ресурсы или отмениться вместе с запросом. Полезный существующий образец разделения глобального владельца и Location-сервисов — Session execution, но без переноса Marketplace в чат-сессии.

Минимальный снимок операции:

- ID, idempotency key, вид действия, целевой источник/пакет, исходная Location;
- `queued | running | cancelling | succeeded | failed | cancelled | interrupted`;
- этап, начальное/последнее время, реальные счётчики с единицами;
- результат, структурированная ошибка или предупреждения;
- номер версии снимка для отбрасывания запоздавших событий.

Закрытый union состояний — единственный источник жизненного цикла. Не добавлять независимые флаги `isInstalling`, `isBusy`, `isCancelled` рядом с ним. Пользовательское согласие на доверие и конфликты хранится как явная часть принятого действия; очередь не должна автоматически включать `force`.

### Очередь и конфликты

Первый вариант: одна выполняющаяся изменяющая операция на реестр, остальные приняты и видны в очереди. Чтение уже загруженного состояния и работа приложения не блокируются. Это проще и надёжнее параллельных загрузок, которые в конце сталкиваются на общей ревизии.

Каждый следующий worker читает актуальное состояние перед выполнением и повторно проверяет целевой ресурс. Нельзя просто переиспользовать `expected_revision` из момента нажатия кнопки: предыдущая операция очереди уже могла её изменить. При изменении выбранной версии, плана, доверия или конфликтов требуется повторное подтверждение, а не скрытая перезапись.

Все пути записи — Web, Desktop, CLI, TUI — должны проходить через один диспетчер. Двойное нажатие или повтор запроса с тем же idempotency key возвращает ту же операцию. Удаление источника, пока из него идёт установка, и одновременные install/uninstall одного пакета должны иметь явный порядок или отказ с понятной причиной.

Параллельную подготовку разных пакетов можно добавить позже с ограничением числа загрузок и отдельной сериализацией фиксации. Для первой версии она не обязательна.

### Состояние источника отдельно от наличия записи

Источник может быть сохранён и находиться в `checking`, `ready`, `failed` или `disabled`. Не удалять адрес из списка из-за сетевой ошибки: показывать причину и «Повторить». Не маркировать источник подключённым только потому, что он уже записан в SQLite.

Снимок представления должен читаться без сетевого обновления всех каталогов. Обновление каталогов — отдельная операция. После изменения достаточно вернуть зафиксированный результат и событие инвалидации, а не держать ответ открытым ради посторонних источников.

### Предварительное подтверждение установки

`plan()` тоже выполняет сеть, поэтому его нельзя оставить скрытым блокирующим исключением. Подготовка плана получает собственный статус. После неё показываются версия, совместимые/неподдерживаемые компоненты, доверие и конфликты. Если пользователь ушёл из панели, уведомление предлагает открыть готовый план, но не открывает модальное окно самовольно.

Подтверждение связывается с конкретным планом/commit. Если к началу установки он изменился, нужно запросить новое согласие.

### Отмена, разрыв связи и рестарт

- Закрытие панели/окна, разрыв SSE или клиентский таймаут не равны отмене серверной работы.
- Отмена — отдельная команда. До фиксации она останавливает сеть/дочерний Git-процесс, удаляет staging и оставляет прежнюю установку активной.
- Короткую транзакцию применения не обрывать посередине. Если результат уже зафиксирован, сообщить об этом; обратное действие — отдельное удаление/восстановление, а не ложное «Отменено».
- Сохранять принятую работу и конечные результаты в SQLite. Частые проценты не превращать в durable event log и не писать в историю чат-сессии.
- Начальная политика восстановления: незавершённые активные операции после рестарта помечаются `interrupted` с доступным повтором. Автоматическое продолжение произвольного этапа не обещать без отдельного протокола восстановления.
- Итог фиксации операции и ревизию реестра нужно согласовать транзакционно. Иначе сбой между записью установки и записью «готово» создаст ложную ошибку уже установленного пакета.
- Установка, зафиксированная в реестре, и последующая проблема загрузки конфигурации должны различаться. Показывать «Установлено, есть предупреждение», а не предлагать повторную установку как будто записи не было.

## Транспорт и клиент

Реализованный экспериментальный API (под флагом):

- `POST /api/experimental/marketplace/operations` — принять действие; ответ `202` со снимком операции;
- `GET /api/experimental/marketplace/operations` и `.../:id` — текущие операции/история и восстановление после переподключения;
- `POST .../:id/cancel` — запросить отмену;
- событие `marketplace.operation.updated` через существующую серверную шину/SSE.

События содержат версионированный снимок операции, а не только дельты счётчиков. На переподключении клиент получает свежий список и согласует его с событиями по версии. SSE — доставка, SQLite/снимок — источник истины. Отдельный WebSocket и частый polling не нужны; редкое резервное чтение при недоступной подписке допустимо.

Общая модель операций должна жить в server controller (`packages/app/src/runtime/server/runtime.tsx`), а не в `MarketplacePanel`. Подписка — на уровень сервера, не только `event.location(directory)`, иначе смена проекта скроет глобальную установку. Представление разделяется по серверу, чтобы операции `4410` не смешивались с основным сервером.

Web и Desktop используют эту модель, существующие `Loader`/toast и компактный список операций. CLI по умолчанию наблюдает до завершения, печатает прогресс в stderr и конечный JSON в stdout; для запуска без ожидания возможен явный флаг. TUI наблюдает тот же ID вне блокирующего диалога. Нельзя выводить прогресс CLI в stdout и ломать машинное чтение JSON.

MCP OAuth — отдельное пользовательское действие после установки: «Пакет установлен; требуется вход в cloudflare-api». Не считать отсутствие авторизации ошибкой скачивания и не держать установку бесконечно активной до входа.

## Решение по «Обновить всё»

Рекомендуемый UX — независимый результат каждого пакета: успешные обновления остаются применёнными, неудачные сохраняют прежнюю версию; итог «6 обновлено, 2 с ошибкой» и повтор только неудачных. Для этого у родительской операции нужны дочерние результаты и фиксация каждого пакета отдельно.

**Это согласованное изменение семантики.** Новый API операций использует независимые фиксации и `outcomes`; прежний синхронный endpoint доступен только без флага и сохраняет атомарный `updateAll()`. Клиенты при доступном API операций используют новый путь. Неудачный пакет можно подготовить повторно отдельно, не переустанавливая успешные.

## Порядок реализации и проверки

1. Согласовать очередь, отмену и семантику массового обновления. Новое поведение оградить флагом в `packages/schema/src/config/flag.ts`; точечные исправления источников флага не требуют.
2. Добавить browser-safe контракты в Schema, минимальное хранение операций и process-global dispatcher в Core. Не нарушать направление зависимостей Schema → Protocol/Core → Server.
3. Инструментировать реальные этапы service/cache/Git, отделить cached view от сетевого refresh, определить границу атомарного применения и согласовать её с записью результата операции.
4. Добавить экспериментальные endpoints и SSE manifest; выполнить `bun run generate` из `packages/client`. Экспериментальные маршруты менять вместе со всеми клиентами, без параллельной неявной очереди на клиенте.
5. Подключить server-level модель Web/Desktop, локальные статусы карточек и центр операций; затем CLI/TUI.
6. Проверить: закрытие/повторное открытие панели, потерю SSE, перезагрузку страницы, два окна, смену проекта/сервера, повтор запроса, конфликт ревизий, отмену на каждом этапе, рестарт до/после фиксации, ошибку Git, 429, невалидный каталог, сбой применения конфигурации и MCP OAuth. Использовать управляемые часы и сигналы завершения, а не реальные минутные ожидания в тестах.

Итог: неблокирующее наблюдение за реальной серверной работой, без выдуманного процента, потери результата при закрытии окна и гонок общей ревизии. Первое внедрение лучше сделать с простой серверной очередью; красивый toast поверх нынешнего длинного HTTP-запроса этих проблем не решает.
