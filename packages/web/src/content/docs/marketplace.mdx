---
title: Marketplace
description: Publish, install, and control OpenCode plugins, skills, and MCP servers.
---

The Marketplace installs related plugins, skills, MCP servers, commands, agents, and instructions as one managed
package. Open **Settings → Marketplace** in the desktop app, or run **Marketplace** from the TUI command palette.

An installed package can remain installed while it is disabled. You can also enable or disable each declared skill
and MCP server independently.

Marketplace sources, installed-package state, and component switches are stored in OpenCode's local application
registry, not in `opencode.json` or `opencode.jsonc`. The active install plans are projected into the effective
configuration in memory. Installing, updating, disabling, or removing a package therefore leaves the user's config
file unchanged.

Run `opencode plugin marketplace export --name team` to export the installed set as a portable profile. Source
request headers, installation receipts, and other local implementation state are omitted from the export.

## Add a catalog

Open the **Sources** tab in the desktop app. In the TUI, open **Marketplace sources** or press `Ctrl+S` from the
Marketplace.

You can also add a source without opening the TUI:

```bash
opencode plugin marketplace add https://git.example.com/ai/agent-marketplace.git
```

A source can be:

- an HTTPS URL to a Marketplace JSON file;
- a GitHub repository URL;
- `github:owner/repository`;
- an HTTP loopback URL for local development.

For Git repository URLs ending in `.git`, OpenCode looks for `.opencode/marketplace.json` through the conventional
GitHub, GitLab, and Gitea raw-file routes. You can pass `--name` to set a display name or `--trust private` for a
private catalog.

OpenCode preserves installation receipts even if a source is disabled, unavailable, or removes an item. This lets
you safely manage or uninstall an existing package.

Catalogs are labelled `official`, `verified`, `community`, or `private`. Official and verified provenance is
reserved for catalogs distributed by OpenCode; user-added catalogs can be community or private. The label does not
sandbox installed code. Private sources can include request headers in `marketplace.sources`; keep credentials out
of project configuration.

## Catalog format

A catalog uses the `opencode.marketplace/v1` schema:

```json title=".opencode/marketplace.json"
{
  "schema": "opencode.marketplace/v1",
  "id": "acme",
  "name": "Acme Marketplace",
  "items": [
    {
      "id": "review-suite",
      "name": "Review Suite",
      "description": "Review changes with reusable workflows and documentation tools.",
      "kind": "plugin",
      "version": "1.0.0",
      "publisher": {
        "name": "Acme"
      },
      "icon": {
        "src-light": "./assets/review-suite-light.png",
        "src-dark": "./assets/review-suite-dark.png"
      },
      "brand_color": "#10A37F",
      "install": {
        "plugins": ["@acme/opencode-review@1.0.0"],
        "skills": {
          "items": [
            {
              "id": "review",
              "name": "review",
              "description": "Review the current changes.",
              "path": "./skills/review"
            },
            {
              "id": "release-notes",
              "name": "release-notes",
              "description": "Prepare release notes.",
              "path": "./skills/release-notes"
            }
          ]
        },
        "mcp": {
          "docs": {
            "type": "remote",
            "url": "https://docs.example.com/mcp"
          }
        }
      }
    }
  ]
}
```

Use a stable, colon-free identifier for the catalog, each item, and each skill.

### Plugin icons

Each item can have its own arbitrary image. For one image, use the short form:

```json
{
  "icon": "./assets/review-suite.png"
}
```

To provide theme-specific artwork, use `src-light` and optionally `src-dark`:

```json
{
  "icon": {
    "src-light": "./assets/review-suite-light.png",
    "src-dark": "./assets/review-suite-dark.png"
  }
}
```

Icon values can be a `./` path relative to the catalog file, an absolute HTTP or HTTPS URL, or a base64 PNG, JPEG,
WebP, or GIF data URL. Relative paths must stay inside the catalog directory. If an image is missing or cannot be
loaded, the desktop app displays a colored initial-based fallback. `brand_color` accepts a six-digit hex color for
that fallback and the icon background.

### Individually controlled skills

Declare skills under `install.skills.items` so the GUI and TUI can show a named switch for each one. Each item needs
an `id` and the actual skill `name`; it can point to a dedicated `path` or `url`. Multiple skills may share a source.
When a named skill is disabled, OpenCode also filters it from runtime skill discovery.

Legacy `install.skills.paths` and `install.skills.urls` arrays remain supported. Each unlabelled source appears as
one switch derived from its path or URL.

### Other install-plan fields

An install plan can also define:

- `plugins`: package strings or `[package, options]` tuples accepted by the `plugin` configuration field;
- `agents`: named agent and subagent configuration;
- `commands`: named slash commands;
- `mcp`: named local or remote MCP server configuration;
- `instructions`: persistent instruction paths or URLs.

Before an install replaces an existing plugin, agent, command, or MCP server, OpenCode shows the conflicting paths
and requires confirmation.

## Enable and disable components

The desktop details panel contains switches for the complete plugin, every declared skill, and every MCP server.

In the TUI:

- press `Enter` on an installed item to manage its components;
- press `Space` in the Marketplace list to enable or disable the whole plugin;
- press `Enter` on a component to toggle it;
- press `Ctrl+D` in the component view to uninstall the package.

Disabling the complete plugin removes its active configuration but keeps the installation receipt and individual
choices. Enabling it restores the plugin and all skills that were not disabled individually.

Enabled MCP servers start automatically when the plugin is enabled. If you explicitly disable an MCP server, that
choice is remembered: toggling the complete plugin off and on does not start that server. Enabling the MCP switch
again makes it eligible for automatic startup.

Uninstalling restores previous values recorded by the installation receipt. Values changed by the user after
installation are preserved rather than overwritten.

## Updates and unavailable catalogs

Marketplace updates use the same receipt mechanism as installation. OpenCode compares semantic versions when
possible and also detects changed item fingerprints. A catalog cannot turn **Update all** into an implicit
downgrade: a lower semantic version remains installed.

Installed items remain visible and removable when their source is disabled, deleted, offline, or no longer
publishes the item. OpenCode reconstructs the entry from its local receipt and snapshot.

## Security

Marketplace is a discovery and configuration mechanism, not a sandbox.

- Plugins execute code inside OpenCode.
- Local MCP servers execute commands on your machine.
- Remote MCP servers receive requests and may require credentials.
- Skills and instructions influence agent behavior.
- Agents and commands can change model, tool, and permission configuration.

Review the publisher, source, repository, requested capabilities, and resulting configuration before installation.
Prefer trusted catalogs for executable plugins and pin package versions when reproducibility matters.

## Local registry, artifact cache, and API

Marketplace runtime state is stored in the OpenCode SQLite database. Sources, installed packages, component switches,
artifact references, and the monotonic registry revision are application state and are never written to
`opencode.json` or `opencode.jsonc`.

Catalog responses, exact item manifests, icons, remote skill files, and remote instruction files are stored in a
SHA-256 content-addressed cache under the OpenCode cache directory. Remote skills and instructions are materialized
into immutable local trees before their install plan becomes active. Catalog refresh uses conditional HTTP requests
when ETag or Last-Modified metadata is available and falls back to the last validated cached response while offline.

The desktop app and TUI use the dedicated `/marketplace` API. Every mutation sends the revision it observed. A stale
client receives a revision conflict instead of silently overwriting another client. Installation and update also
separate planning from execution so trust warnings and configuration conflicts can be reviewed before executable
content is activated.

This feature is still under development. OpenCode creates the Marketplace tables as part of the normal database
schema migration, but it intentionally does not import state from experimental `registry.json` files or Marketplace
configuration written by earlier development commits.
